§0 結論サマリー（30 秒で読む）

会場で確実に動かす鍵は 「自分で AP（親機）を持つこと」 の 1 点に尽きる。 共用 WiFi と iPhone テザリングは、どちらも 端末同士の通信を遮断するため、Mac ↔ ESP32 の LAN 通信には使えない。 推奨は 1 位トラベルルーター、2 位 Mac のインターネット共有（元 = iPhone USB）。 LAN が全滅した時の保険は、簡単な順に「保険 1 = Cloudflare Tunnel ＋ HTTPS ロングポーリング」「保険 2 = MQTT（HiveMQ）」。

推奨構成 ベスト 4（1〜2 位が本命 / 3〜4 位が保険）

1 位 ／ 本命

トラベルルーターを持ち込む

なぜ
自分のサブネット（192.168.8.0/24）を丸ごと持ち歩ける。SSID・パスワード・IP が会場によらず固定なので 焼き直しが一切要らない。クライアント分離も自分で OFF にできる。WAN 側はスマホテザリングでも会場 WiFi でも良い（Repeater/WISP モード）。
準備
GL.iNet GL-SFT1200 Opal 約 $31〜34（約 4,700〜5,100 円）または GL-MT3000 Beryl AX（実売 9,500〜13,600 円）を今日発注。前日に自宅で初期設定 10〜15 分＋Mac の DHCP 予約。
当日の切替 2〜3 分

2 位 ／ ルーターが間に合わない時

Mac のインターネット共有
（元 = iPhone USB → 先 = Wi-Fi）

なぜ
macOS は Wi-Fi→Wi-Fi の共有はできないが、iPhone を USB テザリングにすれば Wi-Fi 側を AP にできる。Mac が 192.168.2.1 固定のゲートウェイになり、ESP32 の接続先 URL も固定できる。追加ハードウェア 0 円。
準備
Lightning/USB-C ケーブル、iPhone のインターネット共有 ON、Wi-Fi オプションで SSID 固定・WPA2/WPA3 混在・チャンネル 1/6/11（2.4GHz）。前日に自宅で通し検証。
当日の切替 5 分

3 位 ／ 保険 1（LAN 全滅時の第一手）

Cloudflare Tunnel（Quick Tunnel）
＋ 機器側は HTTPS ロングポーリング

なぜ
cloudflared tunnel --url http://localhost:3000 の 1 コマンドで https://<ランダム>.trycloudflare.com が生える（アカウント作成すら不要）。Next の Route Handler /api/devices/poll を最大 20 秒 hold するだけなので、Next 側に新規ライブラリは不要、ESP32 も標準の HTTPS クライアント 1 本で済む。ブローカーも外部サービスの契約も要らない。コスト 0 円。
準備
brew install cloudflared と、ロングポーリングの Route Handler（30〜60 行）。機器側は「20 秒 GET → コマンドが来たら実行 → 結果を POST」のループ。ngrok 無料は 20,000 リクエスト/月でポーリングだと 1 日で使い切るため、この用途は Cloudflare を使う。
当日の切替 2〜3 分（URL を env に貼るだけ）

4 位 ／ 保険 2（条件が合うときだけ）

MQTT クラウド中継（HiveMQ 無料）

なぜ
外向き 443/8883 はほぼ確実に通り、Mac も ESP32 も外へ出て行くだけなのでクライアント分離・IP 変動を気にしない。ただしブローカーの契約とクレデンシャル、ESP32 側の MQTT ライブラリが増える。採用するのは「ESP32 の WSS が不安定で WS を諦める場合」か「複数機器への一斉配信（pub/sub）が要る場合」だけ。
準備
HiveMQ Cloud Serverless 無料アカウント（100 接続 / 10GB 月）。ESP32 は PubSubClient + WiFiClientSecure、setBufferSize(2048) 必須。実装 1〜2 時間。
当日の切替 1 分（env 差替のみ）

保険の順序を MQTT から入れ替えた理由は 3 つ。 ① Cloudflare Tunnel はブローカーという別サービスを立てずに済み、アカウント作成もクレデンシャル管理も不要（1 コマンドで URL が生える）。 ② 既にある Next の Route Handler をそのまま外に公開するだけなので、サーバー側の新規実装が最小（MQTT はトピック設計・冪等化・LWT が付いてくる）。 ③ ESP32 側が標準 HTTPS クライアントだけで動く（MQTT ライブラリとバッファ設定の罠がない）。本命が LAN 直結であることは変わらない。

やってはいけない 2 つ

禁止 1

iPhone テザリング直下で Mac ↔ ESP32 を通信させる

なぜ
iOS 18 以降、Apple が配下クライアント同士の IPv4 通信を意図的に遮断している（Apple DTS 明言）。全端末が 192.0.0.2 を名乗り、ブロードキャスト／マルチキャストも届かない。ESP32 は「IP 取得済み・インターネットも使える」のに Mac から一切見えないという、最も紛らわしい失敗になる。
代わりに
iPhone は WAN 回線としてのみ 使う（ルーターの WAN、または Mac の USB テザリング元）。
デバッグに 1 時間溶かす

禁止 2

会場共用 WiFi だけを頼りにする

なぜ
ゲスト SSID の既定はクライアント分離 ON。さらに 2.4/5GHz が別 VLAN だと同一 SSID でも不通、キャプティブポータルは ESP32 が踏めない、WPA2-Enterprise は当日作業に不向き、DHCP リースが短く IP が動く。成否が会場運営次第で、事前に検証できないのが最大の問題。
代わりに
共用 WiFi は「Mac のインターネット回線」または「ルーターの WAN 側」としてだけ使う。
到着後に判明して詰む

§1 悩み → 回答の対応表

事前に挙がった 4 つの悩みに 1 対 1 で答える。結論だけ読んで、気になる行の詳細セクションへ飛ぶ。

悩み結論（1 行）根拠詳細
① 会場では自分のスマホのテザリングと共用 WiFi が使える どちらもそのままでは機器間通信に使えない。両方とも「インターネットへの出口」として扱い、LAN は自分で作る（トラベルルーター or Mac 共有）。 iOS 18+ はクライアント間 IPv4 を遮断（Apple DTS）。ゲスト WiFi はクライアント分離が既定。 §3 §2
②-a ESP32／スタックちゃんへの IP の指定・そもそもどう接続するのか 機器 → Mac の向きに繋ぐ（ESP32 が WebSocket クライアント、Mac が サーバー）。こうすると Mac が機器の IP を知る必要がなくなり、指定するのは「機器側に 1 つだけ書く Mac の URL」に減る。 調査 A-2：IP 変動耐性・AP アイソレーション耐性・同時接続数の観点で逆向き接続が最強。既存実装も STACKCHAN_WS_URL の WS 前提。 §4 §5
②-b 他の人とポート／IP が被らないか 被らない。調整も不要。ポートは IP ごとの名前空間なので、隣のチームの 3000 と自分の 3000 は無関係。IP は DHCP が重複しないよう配る。100 台が同じ SSID にいても、届くかどうかを決めるのは「クライアント分離が有効か」だけ。 調査 C-1（RFC 5227 / ベンダー文書）。気にするのは自分の Mac 内の EADDRINUSE だけ。 §5
②-c IP が変わるたびに焼き直しが大変 焼き直しは完全に不要にできる。(1) WiFi 資格情報は WiFiManager / SD の wifi.txt / NVS で外出し、(2) 接続先 URL は機器の設定画面か /dev からの実行時上書きで変更、(3) そもそも逆向き接続なら Mac 側の IP 指定は 1 箇所。 調査 A-4 / A-5 / C-2。.env.local は再起動が要るのでデモ中は使えない → /dev で実行時上書き。 §5
②-d MacBook やスマホを WiFi（AP）にできないか MacBook は条件付きで可：Wi-Fi→Wi-Fi 共有は不可だが、iPhone USB テザリングを元にすれば Wi-Fi を AP にできる（推奨 2 位）。iPhone のテザリングは AP にはなるが端末間通信が遮断されるので不可。Android テザリングは機種依存で有望（要現物テスト）。 調査 B-3 / B-2。Android は全面遮断が仕様化されておらず多くの機種で ping 可。 §3
③ そもそも ESP32／スタックちゃんを WS/HTTP で接続できるのか（共用 WiFi に繋げるか・PC 無しで単体で繋げるか） できる。PC は不要。ESP32 は単体で Wi-Fi Station として接続し、HTTP サーバー／クライアント、WebSocket サーバー／クライアントのいずれにもなれる。ただし 2.4GHz 専用、キャプティブポータルは踏めないので共用 WiFi の種類次第。スタックちゃんは robo8080 / yh1224 系ファームなら最初から HTTP の口がある（/chat?text=..）ので即日疎通できる。 調査 A-1 / A-2 / A-3。 §4
④ Electron はこの MacBook で起動する。localhost で通信できるのか できる。しかも最も簡単な部分。同一 Mac 内なら 127.0.0.1 のループバックで完結し、Wi-Fi・ファイアウォール・CORS・ローカルネットワーク権限のすべてと無関係。ただし localhost と書かず 127.0.0.1 と書く（::1 に解決されて ECONNREFUSED になる罠）。現行の DESKTOP_BASE_URL=http://127.0.0.1:8792（モック）を実機 Electron のポートに差し替えるだけ。 調査 C-3 / C-4。Node 17+ の verbatim DNS 解決。 §6

§2 接続構成の決定木

上から順に答えていくと構成が 1 つに決まる。分岐の順番は「安定性 × 準備の少なさ」で並べてある。 どの葉に落ちても、§7 の保険 1（Cloudflare Tunnel ＋ HTTPS ロングポーリング）は並行して用意しておくのが前提。

どの葉でも共通でやること：① ESP32／スタックちゃんは WS クライアントとして Mac に繋ぎに行く、 ② 機器の LCD に「IP / 接続先 URL / 接続状態」を常時表示する、 ③ /dev から接続先を実行時に上書きできるようにする、 ④ USB シリアル入口を 1 本用意しておく。

§4 ESP32／スタックちゃんは接続できるのか

結論：できる。PC は不要で、ESP32 単体が Wi-Fi Station として接続する。 HTTP サーバー／クライアント、WebSocket サーバー／クライアントのすべてが可能。 ただし 2.4GHz 専用、キャプティブポータルは踏めないという 2 つの絶対制約がある。 推奨は 「機器が WS クライアントとして Mac のサーバーへ繋ぎに行く」。

§5 IP・ポートの疑問を解消

結論は 3 つ。(1) ポートは他人と絶対に被らない（調整不要）、(2) IP は DHCP が重複しないよう配る、 (3) 届くかどうかを決めるのはクライアント分離だけ。 IP 変動には 7 つの対策があり、焼き直しは完全に不要にできる。

5-3. 焼き直しを不要にする（Wi-Fi 資格情報の外出し）

「IP が変わるたびに焼き直し」の本質は Wi-Fi の SSID/パスワードと接続先 URL がファームに埋め込まれていること。両方を外に出せば焼き直しは消える。

手法コスト判定やり方
SD の wifi.txt / config.json（AI_StackChan2 系）極低★ スタックちゃんではこれが最速SD を抜いてテキストを書き換えるだけ
WiFiManager（tzapu / RoboMagus fork）低★ ESP32 では最推奨接続失敗時に自動で AP 化（StackChan-Setup）→ スマホで SSID 選択・入力 → NVS 保存。接続先 URL もカスタムパラメータとして入力できる
NVS（Preferences）保存—全手法で併用必須起動時 10 秒で NVS の資格情報を試す
WiFiProv（BLE / SoftAP Provisioning）中次点BLE でスケッチが肥大しパーティション変更が要る
Web 設定ページ /settings中併設推奨yh1224 版は最初から JSON PUT で SSID を変えられる
SmartConfig / ESP-Touch低保険成功率が環境依存
シリアル経由 SET_WIFI低最後の砦USB で繋げば必ず通る

推奨 3 段フォールバック：起動 → NVS の資格情報で 10 秒試行 → 失敗したら SD の wifi.txt → それも無ければ WiFiManager の AP モード（StackChan-Setup）に落ちる。

5-4. Next.js（Node）から LAN 機器へ届けるときの注意

  • 必ず Route Handler（サーバー側）から叩く。ブラウザから直叩きすると Chrome 142 の Local Network Access で権限プロンプト／ブロックになる。Route Handler 内の fetch なら CORS も Private Network Access も無関係（README にも明記済みのルール）。
  • AbortSignal.timeout(1500) を必ず付ける。fetch は既定でタイムアウトしないので、機器が無応答だと永久に待つ（エラーは TimeoutError）。
  • macOS ファイアウォールは受信のみ制御。listen 時の「node の接続を許可」ダイアログは許可する。デモ中は FW オフが最速。
  • macOS Sequoia+ の「ローカルネットワーク」権限：Terminal 起動の CLI は対象外だが Electron（GUI アプリ）は確実に対象。症状が「無言でタイムアウト」なので気づきにくい。
  • Node 22 のグローバル WebSocket クライアントは stable（22.4+）。サーバー側は ws が必要。HMR でインスタンスが増殖しないよう globalThis シングルトンにする。

§6 Electron と localhost

結論：同じ MacBook で動かすなら、これは全体で一番簡単な部分。127.0.0.1 のループバックは NIC を通らないので、 Wi-Fi の状態・ファイアウォール・CORS・ローカルネットワーク権限のすべてと無関係に通る。 現行実装は DESKTOP_BASE_URL=http://127.0.0.1:8792（モック）なので、実機 Electron のポートに差し替えるだけ。

§7 LAN が使えない時の代替（クラウド中継）

会場の外向き 443/TLS はほぼ確実に通る。つまり 全員が外のサーバーへ「出て行く」形にすれば、 クライアント分離も IP 変動も AP の種類も一切関係なくなる。 この中でいちばん簡単なのは Cloudflare Tunnel（Quick Tunnel）＋ HTTPS ロングポーリング（保険 1）で、 MQTT（HiveMQ Cloud 無料）は保険 2——ESP32 の WSS が不安定で WS を諦める場合や、複数機器への一斉配信が要る場合に使う。 さらに下の保険として Tailscale（ESP32 非対応）と BLE。いずれもコスト 0 円。

7-3. MQTT の実装メモ（最頻出のハマりどころ）

  • ESP32 の PubSubClient は既定バッファ 256B。setBufferSize(2048) を必ず呼ぶ。これが最頻出の失敗。
  • WiFiClientSecure + setInsecure() でまず動かす。setKeepAlive(15)。TLS ハンドシェイクで数十 KB のヒープを食うので heap_caps_get_free_size をログに出す。
  • トピック設計：hack/<team>/<deviceId>/cmd | res | state(retain) | lwt。request_id で相関、cmd は QoS1（冪等化必須）、テレメトリは QoS0、LWT は必ず設定。
  • clientId が重複すると相互に切断し合う。デバイスごとに UUID を持たせる。
  • ブローカー選択肢：HiveMQ Cloud Serverless（100 接続 / 10GB 月 / 保持 3 日・SLA なし。有料は $0.34/時 ≒ 約 51 円/時）、EMQX Cloud Serverless（支出上限 0 で無料運用可）、test.mosquitto.org（全世界公開なのでトピックに UUID を必ず入れる）。AWS IoT Core は X.509 証明書必須で当日には重い。
  • 遅延は公開ベンチで RTT 約 300ms、近傍リージョンなら 50〜150ms。会話 UI には十分だが、レールのリアルタイム操作には体感が出る。

7-4. Supabase をクラウドにするか

ローカル Supabase（127.0.0.1:54321）のままでは会場の機器から届かない。機器を Supabase 経由で動かす設計にするなら supabase.com の無料プロジェクト（Tokyo）へ supabase link → db push → env 差替 → anon key + RLS（device_id）が必要。 ただし ESP32 から Realtime WS への直結は非推奨（jhagas/ESPSupabase は Broadcast 未実装、公式 Discussion に未解決の接続不可報告あり）で、 現実解は PostgREST ポーリング（robot_commands を 500ms〜1s で GET、PATCH で done）。 往復 1 秒超で体感が鈍いため、機器制御には Cloudflare Tunnel ＋ ロングポーリング（保険 1）か MQTT（保険 2）を推す。 Supabase 無料プロジェクトは 1 週間無操作で一時停止するので、当日朝に必ず起こしておく。

7-5. 現行コードへの落とし込み

packages/devices は現在 http/rail・http/desktop・ws/stackchan と、トランスポートごとにクライアント実装が分かれている。 ここに トランスポート抽象化（HTTP / WS / MQTT / BLE / シリアル）を 1 枚挟み、RailClient / StackchanClient / DesktopClient のインターフェース（packages/devices/src/types.ts）はそのまま維持する。 具体的には send(envelope) / onInbound(handler) だけを持つ Transport 型を定義し、既存の createRailClient 等はその Transport を受け取る形に変える。 request_id の採番（createRequestId）・タイムアウト・再送は既に wire.ts 側に集約されているので、トランスポートを差し替えても Route Handler と Mastra tool は無変更で済む。 env は DEVICE_TRANSPORT=http|ws|mqtt|ble|serial を 1 本足し、DEVICE_MODE=real と組み合わせる。 これにより当日「LAN 全滅」と判明しても、env 1 行の変更で保険 1（トンネル + ロングポーリング）へ切り替わる（保険 2 の MQTT も同じ口に載る）。

    担当: 本人所要 15 分任意・時間があれば

    いつ要るか：保険 1（Cloudflare Tunnel ＋ HTTPS ロングポーリング）で足りるなら不要。ESP32 の WSS が不安定で WS を諦める場合や、複数機器への一斉配信（pub/sub）が要る場合だけ用意する。なぜ人間か：アカウント作成とクレデンシャル発行は本人確認・同意を伴うため。https://www.hivemq.com/pricing/fully-managed/ の Serverless 無料枠（100 接続 / 10GB 月）。発行したユーザー名・パスワードは <REPO_ROOT>/.env.local に置き、リポジトリにコミットしない。実装（mqtt.js / PubSubClient）はエージェントに委譲できる。

  • ⑦ Tailscale を Mac とスマホに入れる
    担当: 本人所要 20 分前日まで

    なぜ人間か：アカウント作成と各端末での認証・権限許可が必要なため。Personal 無料（6 ユーザー）。ESP32 は非対応なので機器には効かないが、Mac ↔ Electron ↔ スマホの到達性が IP 変動と無関係になる（MagicDNS で名前固定）。入れない理由がないので保険として導入する。Personal プランは非商用向けである点に注意。

  • ⑧ 会場で保険の疎通を確認する（到着直後）
    担当: 本人所要 2 分当日

    なぜ人間か：会場に物理的にいないと実行できないため。まず保険 1：cloudflared tunnel --url http://localhost:3000 が URL を発行し、スマホのモバイル回線からその URL が開けるか。次に保険 2 を使う予定なら：nc -zv <broker-host> 8883 と nc -zv <broker-host> 8884（WSS 保険）。8883 が塞がれている会場があるので両方試す。あわせて §9-2 の 5 分判定を上から実行する。

  • ⑨ Supabase をクラウドに移すか決める
    担当: 本人（設計判断）所要 10 分の判断前日まで

    なぜ人間か：アーキテクチャの方針決定であり、無料枠・停止リスク・移行コストのトレードオフ判断を伴うため。判断材料：機器を Supabase 経由で制御する設計にしないなら、ローカル Supabase のままで良い（Mastra Memory とログ用途のみ）。機器の中継に使うなら、クラウド移行が必須で、かつ往復 1 秒超の遅延を受け入れることになる（MQTT なら 100〜350ms）。推奨は「Supabase はログ用途のみ・機器中継は MQTT」。詳細は §7-4。

  • ⑩ Electron を本番ビルドして画面収録権限を通す
    担当: 本人所要 15 分前日まで

    なぜ人間か：macOS の権限ダイアログは GUI での本人操作が必須（TCC はスクリプトから許可できない）。開発バイナリと本番ビルドは別アプリ扱いなので、当日配る本番ビルドで通しておくこと。権限変更後はアプリ再起動が必要（electron#36722）。詳細は §6-1。
